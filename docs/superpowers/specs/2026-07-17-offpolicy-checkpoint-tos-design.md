# Off-policy Rollout Checkpoint and TOS Storage Design

## Goal

Make fixed-delay off-policy training resume without changing its data stream or
policy lag, and store complete checkpoints directly in TOS through a CloudFS
POSIX mount.

For a checkpoint at policy version `N` with `delay_steps=2`, restoring must
recover the actor at version `N` and queued rollout batches generated by policy
versions `N-2` and `N-1`. The first post-resume update must therefore still
observe `policy_version_lag=2`.

## Checkpoint Layout

Each committed checkpoint uses this layout:

```text
global_step_N/
  actor/
  data.pt
  metrics.jsonl
  rollout_buffer/
    batch_0.pkl
    batch_1.pkl
    manifest.json
  _SUCCESS
```

`manifest.json` records a schema version, checkpoint step, configured delay,
rollout generation step, queue order, behavior-policy version, file size, and
SHA-256 checksum for each batch. `DataProto.save_to_disk()` and
`DataProto.load_from_disk()` provide the batch serialization format.

The rollout buffer owns `state_dict`, `save`, and `load` behavior. The trainer
only coordinates it with actor and dataloader checkpointing.

## Commit Protocol

Checkpoint publication is fail-closed:

1. Save actor and optimizer shards into `global_step_N`.
2. Save dataloader state.
3. Write every queued rollout to a temporary file and atomically rename it.
4. Write and atomically rename `manifest.json` after validating all sizes and
   checksums.
5. Snapshot metrics and create `_SUCCESS`.
6. Update `latest_checkpointed_iteration.txt` last.

The latest pointer is the commit record. A checkpoint without `_SUCCESS`, with
a missing batch, or with a checksum/configuration mismatch is not resumable.
When fixed-delay mode is enabled, restore must not silently fall back to an
empty buffer.

The rollout buffer and dataloader state must be saved at the same point in the
training iteration. This preserves the invariant that prompts already consumed
by the dataloader are represented either by the completed update or by a queued
rollout.

## Trainer Lifecycle

The trainer creates the rollout buffer before loading a checkpoint and stores
it on the trainer instance rather than in a local `fit()` variable. Saving and
loading also preserve `rollout_generation_step`.

After restoring checkpoint `N`, the actor weights, dataloader cursor, rollout
queue, and generation counter are restored before validation or generation.
Runtime metrics continue to expose behavior/current policy versions, queue
depth, generation step, and policy-version lag.

Trainer-level retention removes whole old `global_step_*` directories only
after a newer checkpoint is committed. This prevents rollout files from being
left behind when actor-level retention removes only actor shards. The formal
recipe keeps the newest two complete checkpoints.

## TOS via CloudFS

The training task mounts the `sia-thu` bucket prefix `users/cxli` through an
MLP-bound CloudFS instance at `/sia-thu/cxli`. The formal recipe sets:

```text
trainer.default_local_dir=/sia-thu/cxli/checkpoints/verl_moe/<experiment>
```

The task YAML must include the actual CloudFS `FileSystemName`; the name must be
read from MLP Global Configuration or the CloudFS API and must never be guessed.
The entrypoint verifies that the mount is writable before starting Ray.

On startup the entrypoint refreshes the checkpoint directory with `cfs-cli ls`
when the command is available. Checkpoints are immutable after `_SUCCESS`, so
the design does not rely on append support. The small latest pointer is the only
overwritten object.

If CloudFS is unavailable or not writable, training exits before model startup.
There is no automatic fallback to vePFS because that would split checkpoints
across storage backends and make restart behavior ambiguous.

## Failure Handling

- Interruption before `_SUCCESS`: ignore the incomplete directory and retain
  the previous latest pointer.
- Interruption after `_SUCCESS` but before pointer update: the checkpoint is
  complete but not selected automatically; the previous checkpoint remains the
  recovery point.
- Corrupt rollout file or manifest mismatch: fail restore with a precise error.
- Delay/config mismatch: fail restore rather than reinterpret queued data.
- Missing CloudFS mount: fail in entrypoint preflight.

## Verification

Unit tests cover buffer round trips, queue order, metadata validation,
corruption detection, delay mismatch, and restoration of generation counters.
Trainer tests verify save ordering, strict restore, complete-directory
retention, and that the latest pointer is written only after `_SUCCESS`.

An end-to-end smoke test runs fixed-delay training through a checkpoint,
terminates it, resumes with the same experiment name, and asserts that the
first resumed training update has `policy_version_lag=2`. A storage preflight
also writes, renames, reads, and deletes a probe under the CloudFS checkpoint
root before the formal task is submitted.
